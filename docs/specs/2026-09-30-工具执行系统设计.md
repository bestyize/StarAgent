## 0. 问题：现在缺的是什么

### 0.1 现状

`AppState.send()`（`core/data/.../AppState.kt:668`）的执行路径是**一次**模型调用：

```
拼 system prompt → 流式请求 → 收文字 → resolveReply 剥 ```task / ```memory 块 → 落库 → 结束
```

没有第二步。`runTask()`（同文件 `:1074`）也是——它把一句
「现在到点了，请把这件事实实在在做一遍」塞给模型，然后收下模型写的**一段文字**。
模型没有网络、没有文件、没有工具，它只能写一段关于这件事的描述。

### 0.2 证据：类型层表达不了多步执行

```kotlin
data class LlmTurn(val role: LlmRole, val text: String, val images: List<MediaAsset>)

sealed interface ChatStreamEvent {
    data class Delta(val text: String)
    data object Completed
    data class Failed(val message: String)
}
```

`core:llm` 全层没有 `tools` / `tool_calls` / `tool_use` 的任何痕迹；`LlmTurn`
没有地方承载"工具调用的结果"。这不是少一个功能，是**核心类型表达不了一次多步执行**。

### 0.3 四个断头路是同一个根因

| 现象 | 根因 |
| --- | --- |
| `MessageBody.Artifact` 只有 `Seed.kt` 造得出来，运行期无生产者 | 没有动作，就没有产物 |
| 技能只有名字和简介，装上不生效 | 技能没有可承载的东西（没有工具可挂） |
| `MessageBody.Execution` / `ExecutionStep` 定义了但从不发射 | 没有循环，就没有步骤 |
| 任务不真执行，靠提示词要求模型"实实在在"做一遍 | 没有工具，模型只能表演 |

四件事不是四个半成品，是**一个缺失的执行内核的四个投影**。

## 1. 范围

### 1.1 本设计要做

1. **工具契约**：定义 / 线格式 / 执行三层分开
2. **两家协议的渲染与解析**：OpenAI 兼容与 Anthropic 的工具调用
3. **agent 循环**：调用 → 执行工具 → 回喂 → 再调用，带迭代上限
4. **首批工具**：记忆、任务、网络（见第 6 章）
5. **执行过程可视化**：让 `MessageBody.Execution` 第一次有生产者
6. **替换现有暗号机制**：`create_task` / `remember` 工具取代
   ` ```task ` / ` ```memory ` 的文本解析（解析器保留，见 4.4）

### 1.2 本设计不做

| 不做 | 原因 |
| --- | --- |
| **权限 / 审批 / 沙箱** | 用户明确暂缓。**代价见 11.1——能力面必须相应收窄** |
| 外部工具 / MCP | 移动端 stdio 不可用；一期工具全是第一方的 |
| 并行工具调用 | 先串行。串行足够跑通，并行是优化 |
| 工具调用的流式进度 | 等整个流结束发一次（见 4.3） |
| 代码执行 / 虚拟 OS | 独立产品线，不在本期 |
| 技能真正生效 | 需要工具先落地，列为后续（见 11.2） |

## 2. 架构总览

### 2.1 新模块与依赖方向

```
core:model  ──→  core:tools  ──→  core:data
 （类型）        （契约 + 注册表     （端口实现
                + 内置工具）        + 循环）
                      ↑
                 core:llm（渲染器）
```

`core:tools` **只依赖 `core:model`**——不认识 AppState、不认识 Compose、不认识 Ktor。
这是它能被独立测试的前提，也是将来接外部工具的接缝。

### 2.2 模块布局

```
core/tools/
├── ToolDefinition.kt        纯数据：name / description / JSON Schema
├── Tool.kt                  执行契约
├── ToolResult.kt            多形态输出
├── ToolRegistry.kt          按名取、可合并
├── host/
│   ├── ToolHost.kt          调用现场：端口 + 是谁在调
│   ├── MemoryPort.kt
│   ├── TaskPort.kt
│   └── WebPort.kt
└── builtin/
    ├── RecallMemoryTool.kt
    ├── RememberTool.kt
    ├── CreateTaskTool.kt
    ├── ListTasksTool.kt
    ├── UpdateTaskTool.kt
    ├── CancelTaskTool.kt
    └── WebFetchTool.kt
```

### 2.3 领域类型放 `core:model` 的先例

`ToolDefinition` / `ToolCall` / `ToolResult` 放 `core:model` 而不是 `core:tools`，
因为 `core:llm` 也要用它们（`LlmTurn` 要带 `toolCalls` / `toolResults`），
而 `core:llm` 不能依赖 `core:tools`（`core:tools` 的实现要调 `core:data` 的端口）。

这跟 `MediaAsset` 当初的处理**完全同构**：`MessageBody.Image` 和 `LlmTurn.images`
都要用它，让领域模型反向依赖平台层是错的，所以上移到 `core:model`。
现在 `core:model` 仍然零平台依赖。

### 2.4 循环的位置

循环留在 `core:data`，抽成新文件 **`AgentLoop.kt`**，不再往 `AppState` 里塞。

理由：循环的本质是驱动对话，而对话就是 `core:data` 的活。把它搬到独立模块
需要造一整套端口（读消息、写消息、busy 标志、LLM 流、工具），端口管道比循环本身还长。
**搬出去换来的收益不抵这个复杂度。** 关键是抽成独立文件——`AppState` 已经 1456 行。

### 2.5 `WebPort` 的实现位置

`WebPort` 由 **`core:data` 实现**，复用 `core:llm` 里现成的 `HttpClientFactory`
（三端引擎已经配好：CIO / OkHttp / Darwin）。需要把它从 `internal` 提到 `public`。

不新建 `core:net` 的理由：改动小，`HttpClientFactory` 本来就是干这个的。
（代价：`core:llm` 带着 HTTP 引擎，将来协议层要独立搬走时不够自足。记在 12.1。）

## 3. 契约设计

### 3.1 领域类型（`core:model`）

```kotlin
/** 工具的静态描述。纯数据，不认识任何协议。 */
data class ToolDefinition(
    val name: String,
    val description: String,
    val inputSchema: JsonObject,     // JSON Schema
)

/** 模型发出的一次工具调用。 */
data class ToolCall(
    val id: String,                  // 回喂时要对上的 id
    val name: String,
    val arguments: String,           // 原始 JSON 字符串，不预先解析
)
```

**`arguments` 保持 `String`，不解析成 `JsonObject`。** 三条理由：

1. 两家协议的原始形状都是字符串，提前解析等于在协议层丢掉原始信息
2. 官方文档明确警告"模型不总是生成合法 JSON"——**非法 JSON 必须是一个可处理的状态，
   不是一个异常**
3. 解析推迟到工具执行前，那里才能把失败变成"给模型看的错误结果"

### 3.2 执行契约（`core:tools`）

```kotlin
interface Tool {
    val definition: ToolDefinition
    suspend fun execute(args: JsonObject, host: ToolHost): ToolResult
}
```

`ToolResult` 有**三种表示**，对应三个不同的读者：

```kotlin
data class ToolResult(
    val callId: String,
    val content: String,             // 给模型：完整、权威
    val isError: Boolean = false,
    val externalContext: Boolean = false,  // 含外部内容 → 本轮不写记忆
    val logText: String? = null,     // 给日志：可以截断
)
```

**为什么 `content` 和 `logText` 要分开**：上下文预算和事后调试是两件事。
日志可以有损、可以截断、可以省略媒体；模型看到的那份必须完整。
（这条来自 Codex 的 `ToolOutput`——它的注释明说：
"A deliberately lossy diagnostic representation... **This is not the authoritative tool result**"。）

**`externalContext` 是记忆的防污染闸门。** `web_fetch` 抓回来的网页里可能写着
"用户喜欢简洁的回答"。这条为真时，**这一轮不产生记忆**。
不设这道闸门，提示注入会顺着工具输出写进长期记忆，而且用户永远不知道
（他只会发现 Agent"记得"一件他没说过的事）。

### 3.3 调用现场

工具**不能是单例**——记忆和任务都是按智能体隔离的，工具必须知道是谁在调：

```kotlin
class ToolHost(
    val memory: MemoryPort,
    val tasks: TaskPort,
    val web: WebPort,
    val agentId: String,
    val conversationKey: String,
)
```

端口是窄接口，由 `core:data` 实现：

```kotlin
interface MemoryPort {
    suspend fun recall(query: String, limit: Int): List<MemoryItem>
    suspend fun remember(category: String, text: String)
}

interface TaskPort {
    suspend fun create(spec: TaskSpec): String
    suspend fun list(): List<TaskSummary>
    suspend fun update(id: String, spec: TaskSpec)
    suspend fun cancel(id: String)
}

interface WebPort {
    suspend fun fetch(url: String): FetchResult
}
```

**端口存在的意义有三条**：
1. 每个工具都能用假端口单测，不用起 AppState
2. 网络被挡在契约外面——`core:tools` 自己不碰 HTTP
3. **端口是将来接外部工具的接缝**（三期的 MCP 从这里进）

### 3.4 注册表

```kotlin
class ToolRegistry private constructor(private val tools: Map<String, Tool>) {
    fun find(name: String): Tool?
    fun definitions(): List<ToolDefinition>
    operator fun plus(other: ToolRegistry): ToolRegistry

    companion object {
        fun of(vararg tools: Tool): ToolRegistry
        val Empty: ToolRegistry
    }
}
```

一期只有内置工具，**但注册表长得像"还能接受别的来源"**——三期加外部工具时不用改结构。
这跟 `MediaPicker` / `MediaSaver` / `LocalStore` 的"契约 + 注册表"是同一套形状。

### 3.5 参数解析：混合方式

**schema 手写，参数用 `@Serializable` data class 解析。**

```kotlin
@Serializable
private data class RememberArgs(val category: String, val text: String)

object RememberTool : Tool {
    override val definition = ToolDefinition(
        name = "remember",
        description = "把关于用户的一条信息存进长期记忆。只在用户明确表达了偏好、" +
            "事实或习惯时调用，不要把每轮对话都记下来。",
        inputSchema = buildJsonObject {
            put("type", "object")
            putJsonObject("properties") {
                putJsonObject("category") {
                    put("type", "string")
                    put("enum", buildJsonArray {
                        add("Preference"); add("Person"); add("Habit")
                        add("Experience"); add("Decision")
                    })
                }
                putJsonObject("text") { put("type", "string") }
            }
            putJsonArray("required") { add("category"); add("text") }
        },
    )

    override suspend fun execute(args: JsonObject, host: ToolHost): ToolResult { ... }
}
```

KMP 里没有可靠的 JSON Schema 生成器（`kotlinx.serialization` 不产 schema）。
手写 schema 配类型化解析是最省事的组合：**schema 写错了模型会调错参数，
但解析层会立刻报错，测得住。**

五个记忆分类直接复用现有的 `MemoryCategory` 枚举
（`Preference` 我的喜好 / `Person` 重要的人 / `Habit` 生活习惯 /
`Experience` 经历历史 / `Decision` 重要决策），
**不新造一套分类**——工具的参数值就是枚举名，两边不会漂移。

**工具描述要写在工具定义上，不是系统提示里。** Anthropic 的工程建议是
"在工具定义上花的功夫要超过提示词"，因为描述跟着工具走，加工具时不会漏。

## 4. 协议层改动

这是**唯一需要动 `core:llm` 的部分**。

### 4.1 渲染：定义 → wire 格式

```kotlin
internal object ToolRenderer {
    fun openAi(defs: List<ToolDefinition>): JsonArray   // {type:"function", function:{...}}
    fun anthropic(defs: List<ToolDefinition>): JsonArray // {name, description, input_schema}
}
```

差异只有两点：外面包不包 `function` 层、schema 的键叫 `parameters` 还是 `input_schema`。

### 4.2 解析：wire 格式 → ToolCall

**这里两家差别大得多，是真正会写错的地方。**

| | OpenAI 兼容 | Anthropic |
| --- | --- | --- |
| 停止标志 | `finish_reason: "tool_calls"` | `stop_reason: "tool_use"` |
| 调用在哪 | 消息上的 `tool_calls` 数组 | content 块流里的 `tool_use` 块 |
| 参数形状 | `function.arguments`，**字符串** | **`input_json_delta` 片段，要自己拼** |
| 回喂形状 | `{role:"tool", tool_call_id, content}` | **user 消息**里的 `tool_result` 块 + `tool_use_id` |

**难点一：OpenAI 的 `arguments` 跨多帧拼接。**

```
data: {"tool_calls":[{"index":0,"function":{"name":"remember","arguments":"{\"ca"}}]}
data: {"tool_calls":[{"index":0,"function":{"arguments":"tegory\":\"pref\""}}]}
data: {"tool_calls":[{"index":0,"function":{"arguments":",\"text\":\"爱吃辣\"}"}}]}
```

必须**按 `index` 累积**到一个缓冲区，流结束时才完整。名称和参数可能在不同帧里。

**难点二：Anthropic 的 `input` 在流式下不是现成对象。**

非流式时 `input` 是解析好的对象；但你走的是 `stream: true`，
实际收到的是 `input_json_delta` 事件，里面是**片段字符串**，同样要累积拼接。
**以实际 SSE 事件为准，不要按非流式的形状写。**

### 4.3 流式事件扩展

```kotlin
sealed interface ChatStreamEvent {
    data class Delta(val text: String) : ChatStreamEvent
    data class ToolCallsReady(val calls: List<ToolCall>) : ChatStreamEvent   // 新增
    data object Completed : ChatStreamEvent
    data class Failed(val message: String) : ChatStreamEvent
}
```

**累积的职责在 `core:llm`，不在循环里。** 上层只收到"一组完整的 ToolCall"——
两家协议差异大、但上层完全一样，把差异关在协议层内部。

**粒度：等整个流结束发一次**，不做每个 call 拼完就发。
模型这一轮只输出工具调用、不输出正文，用户本来没什么可看的；
早点知道"要调 X"价值不大，复杂度实实在在。将来要更细的进度再拆。

### 4.4 `LlmTurn` 扩展与现有解析器的去留

```kotlin
data class LlmTurn(
    val role: LlmRole,
    val text: String,
    val images: List<MediaAsset> = emptyList(),
    val toolCalls: List<ToolCall> = emptyList(),      // assistant 带工具调用
    val toolResults: List<ToolResult> = emptyList(),  // 回喂
)
```

**回喂位置两家不同**：OpenAI 是 `role:"tool"` 的**独立消息**；
Anthropic 是 `role:"user"` 消息里的 **content 块**。
Anthropic 那侧要把 `toolResults` 塞进 user 消息的块数组——
**跟图片走的是同一套机制**（`putAnthropicContent` 已经在拼块数组了），复用那个思路。

**`TaskBlock` / `MemoryBlock` 的文本解析保留，不删。** 它有三个用途：

1. **降级路径**：不支持工具调用的服务商，靠它。见 4.5
2. 历史存档里的旧消息仍需要它渲染
3. 删除是独立决定，不该捆在这次改动里

但**系统提示不能再同时要求两套**。`systemPromptFor()` 改成条件注入：

```
发工具时     → 不发 TaskBlock.INSTRUCTION / MemoryBlock.INSTRUCTION
不发工具时   → 照旧发（降级路径）
```

同一件事只给模型一种做法，否则它会两套都用（既建任务又吐 ```task 块）。

### 4.5 服务商不支持工具调用怎么办

**这是必须处理的情况**：一期承诺"模型自由"，用户填任意服务商，
而 `tools` 参数的支持程度参差不齐——有的直接 400，有的一直接受但从不真的调用。

因为三层是分开的，**降级不是第二套系统，只是第三个渲染器**：

```
内部 Tool 模型
  ├─ renderOpenAiTools()     → tools 数组
  ├─ renderAnthropicTools()  → tools 数组
  └─ renderAsPromptText()    → 一段说明 + 现有解析器   ← 降级路径
```

现有的 ` ```task ` 暗号机制，本质上就是 `create_task` 工具的"文本渲染"——
**降级路径已经写好了一半。**

**本期实现原生工具调用，降级路径留作后续**（本期先跑通）。
但**三层必须分开**——分开之后补降级是加一个函数，不分开就是重写。

## 5. 循环设计

### 5.1 位置与形状

`core/data/.../AgentLoop.kt`：

```kotlin
internal class AgentLoop(
    private val llm: suspend (LlmEndpoint, List<LlmTurn>) -> Flow<ChatStreamEvent>,
    private val registry: ToolRegistry,
    private val maxIterations: Int = 8,
) {
    suspend fun run(
        endpoint: LlmEndpoint,
        history: MutableList<LlmTurn>,
        host: ToolHost,
        onText: (String) -> Unit,          // 流式文字
        onToolStart: (ToolCall) -> Unit,   // 开始调工具
        onToolEnd: (ToolCall, ToolResult) -> Unit,
    ): LoopOutcome
}
```

**构造函数注入 `llm` 函数而不是直接依赖 `ChatCompletion`**——这样循环能用假 LLM 单测，
不需要起 HTTP。这是它能被测的关键。

### 5.2 循环体

```
iteration = 0
loop:
    iteration++
    if iteration > maxIterations: return Stopped("达到步数上限")

    流式请求(endpoint, history)
      ├ 收到 Delta       → onText(累积)
      ├ 收到 ToolCallsReady(calls)
      └ 收到 Failed      → return Failed

    把 assistant 这一轮（文字 + toolCalls）追加进 history

    if calls 为空: return Done(最终文字)      // 这就是终止条件

    for call in calls:                        // 串行
        onToolStart(call)
        result = 执行(call)
        onToolEnd(call, result)

    把 toolResults 追加进 history
    继续 loop
```

### 5.3 三个必须设的护栏

| 护栏 | 值 | 为什么 |
| --- | --- | --- |
| **迭代上限** | 8 | 防止死循环烧钱。达到上限时**明确告诉用户**，不要静默截断 |
| **单个工具超时** | 30 秒 | 网络工具可能挂住 |
| **输出截断** | 单次工具结果上限（如 8000 字符） | 网页正文可能极长，会把上下文撑爆 |

**迭代上限的失败信息要写成人话**：
「这个任务需要的步骤有点多，我先停在这里。你可以把要求说得更具体一些。」

### 5.4 三个调用点

循环要被三处复用（都用同一个 `AgentLoop`）：

| 调用点 | 现状 | 改动 |
| --- | --- | --- |
| `send(agentId, ...)` `:668` | 单次调用 | 换成循环 |
| `sendToGroup(groupId, ...)` `:831` | 单次调用 × 成员数 | 换成循环 |
| `runTask(task)` `:1074` | 单次调用 | 换成循环——**这是任务第一次真会干活** |

`runTask` 是收益最大的一个：任务从"让模型描述一下"变成"真的去查、真的去记"。

### 5.5 工具注册表怎么给到循环

一期：**所有智能体拿到全部工具**（简单）。技能门控是后续（见 11.2）。

```kotlin
private fun registryFor(agent: Agent): ToolRegistry =
    BuiltinTools.all    // 一期不做技能门控
```

`ToolHost` 的 `agentId` 由调用点传，保证记忆/任务按智能体隔离。

## 6. 首批工具

七个（`web_search` 待定，见 6.3）。

### 6.1 记忆（2 个）

| 工具 | 参数 | 行为 |
| --- | --- | --- |
| `recall_memory` | `query: string` | 从当前智能体的记忆里检索相关条目 |
| `remember` | `category: enum, text: string` | 写入一条记忆 |

**`recall_memory` 是这一批里价值最高的一个**——它把记忆从"静态列表"
变成"参与推理"。现在记忆只能靠系统提示灌最近若干条（`MAX_PROMPT_MEMORIES`），
`recall_memory` 让模型能主动按需查。

**实现注记**：一期没有向量检索，`recall` 先用**关键词匹配**（记忆条数本来就少）。
参数留 `query` 而不是 `id`，是为了将来换向量检索时接口不用改。

### 6.2 任务（4 个）

| 工具 | 参数 | 行为 |
| --- | --- | --- |
| `create_task` | `title, recurrence, schedule, note?` | 建一条托管任务 |
| `list_tasks` | — | 列出当前智能体的任务 |
| `update_task` | `id, ...` | 改任务 |
| `cancel_task` | `id` | 取消任务 |

这**直接替掉 ` ```task ` 暗号**。好处不只是"更规范"：

- 不用再靠正则，不用再担心模型格式跑偏
- 模型能**改**、能**查**、能**删**（现在只能建）
- `create_task` 可以立即返回任务 id，模型能接着引用它

`TaskDraft` / `confirmDraft` 那套"草稿卡片 → 用户点创建"的交互**保留**——
工具执行完仍然弹确认卡片，只是草稿来自工具参数而不是正则。
**确认这一步不能省**：任务是对未来的承诺，不该由模型单方面落库。

### 6.3 网络（1 个，1 个待定）

| 工具 | 状态 |
| --- | --- |
| `web_fetch(url)` | ✅ 可实现——纯 HTTP GET + 正文提取，不需要额外 Key |
| `web_search(query)` | ⚠️ **待定**——需要搜索后端（见 12.2） |

`web_fetch` 的输出**必须标 `externalContext = true`**，否则网页内容会写进记忆。

**HTML 正文提取**：一期用最朴素的办法（去标签 + 折叠空白 + 长度截断），
不引重量级解析库。够用就行，效果不好再升级。

### 6.4 工具描述是产品的一部分

工具描述直接决定模型什么时候调它。三条要求：

1. **说清什么时候不调**——`remember` 要写"不要把每轮对话都记下来"，
   否则模型会把闲聊也塞进记忆
2. **参数名和枚举值自带约束**——`category` 用 enum，模型不会编出第六个分类
3. **描述跟着工具走**，不写在系统提示里——加工具时不会漏

## 7. 界面呈现

### 7.1 执行过程终于有生产者

`MessageBody.Execution` / `ExecutionStep` **已经定义好了但从不发射**——
因为之前没有循环。循环一上，它自然就有了生产者：

```
用户：帮我查一下这个库的最新版本，然后记一下我常用它

  ┌─────────────────────────────┐
  │ ⟳ 正在处理                   │
  │   ✓ 抓取 github.com/…        │
  │   ✓ 记住「常用 OkHttp」       │
  │   完成，共 2 步              │
  └─────────────────────────────┘
```

循环的 `onToolStart` / `onToolEnd` 追加步骤到**同一张卡片**（不是每条一个气泡），
卡片随步骤增长而更新。

### 7.2 一轮流里的顺序

```
用户消息
  ├ 助手文字（如果模型先说了话）      ← 流式
  ├ 执行卡片（工具在跑）              ← 累积更新
  ├ 助手文字（工具跑完后的结论）      ← 流式
  └ …（可能再来一轮）
```

### 7.3 产物卡片仍然没有生产者

`Artifact` 需要一个 `emit_artifact` 工具才会真正活起来。
**本期不做**——理由是产物还要配导出/分享（现在两个 `onClick` 都是空的），
那是独立的一块。记在 11.3。

## 8. 错误处理

每一条都要有明确落点，**默认不许崩**。

| 情况 | 处理 |
| --- | --- |
| `arguments` 不是合法 JSON | 不崩。构造一个 `isError=true` 的结果回喂，内容写"参数格式错误，请重新调用并确保是合法 JSON" |
| 缺必需参数 / 类型不对 | 同上，错误信息里带上缺的字段名 |
| 工具名不存在 | 回喂"没有名为 X 的工具"，附上可用工具名清单 |
| 工具执行抛异常 | 捕获，回喂 `isError=true` + 人话描述。**异常不许穿出循环** |
| 单个工具超时 | 回喂"这个操作超时了" |
| 达到迭代上限 | **停止循环，明确告知用户**（不是静默截断） |
| 流式请求失败 | 保留已收到的部分，按现有 `Failed` 路径处理 |
| 用户点停止 | 走现有 `CancellationException` 路径，保留部分结果 |

**贯穿原则：工具的错误是"给模型看的信息"，不是"给程序的异常"。**
模型看到"参数格式错误"会自己重试；程序抛异常只会让用户看到崩溃。

## 9. 测试策略

### 9.1 `core:llm`：流式拼接（**最关键，必须先写**）

这是最容易出偶发 bug 的地方，用固定期望值钉住：

1. 参数被切成 N 片（N = 1, 2, 3, 7），拼出来的必须一致
2. 名称和参数落在不同帧
3. 多个工具调用（`index` 0 和 1 交错到达）
4. 两家的回喂 JSON 形状——用固定字符串断言
5. **模型吐非法 JSON** → 变成一个合法的 `ToolCall`（原始字符串保留），不崩

**照 `ImagePayloadTest` 的路子写**——它就是"两家格式用固定期望钉住"。

### 9.2 `core:tools`：每个工具用假端口

不依赖 AppState、不依赖 HTTP：

```
假 MemoryPort 记录被写入的内容 → 断言 remember 写对了分类和文本
假 TaskPort   返回固定 id       → 断言 create_task 的参数映射正确
假 WebPort    返回固定 HTML     → 断言正文被提取、externalContext = true
```

外加：每个工具的 `inputSchema` 与它的参数 data class 一致
（用测试确保 schema 没写漏字段）。

### 9.3 `core:data`：循环用假 LLM

用构造函数注入的假 LLM 流，覆盖：

1. 一轮就结束（模型不调工具）
2. 调一次工具然后结束
3. 连续调三次然后结束
4. **达到迭代上限**——断言停止且给出提示
5. 工具返回 `isError=true` 后模型重试
6. `externalContext=true` 时**不写记忆**
7. 用户取消

## 11. 明确不做的

### 11.1 不做权限控制，代价是能力面必须收窄

用户明确暂缓权限控制。这与"给模型真实能力"是**一对取舍**，不能只要前者：

| 工具 | 没有权限闸门意味着 |
| --- | --- |
| 任意 HTTP | 模型可以把用户数据发到任意地址 |
| 文件读写 | 模型能读写整棵存档树，包括 `SOUL.md`、`MEMORY.md` |
| 代码执行 | 模型写的代码在用户手机上执行，没有任何东西拦着 |

**所以本期的能力面必须收窄**，收窄写在工具实现里，不需要权限框架：

- **网络**：只做 `web_fetch`，**不做任意 HTTP**。且只允许 `https`、拒绝内网地址
- **文件**：**本期不做文件工具**（要设计路径边界，独立议题）
- **代码**：**本期不做代码执行**

这不是"以后再补权限"的临时状态——**这是本期有意选择的能力边界**。
将来加权限闸门时，上面三样才能放开。

### 11.2 技能真正生效（后续）

技能现在只有 `name / summary / glyph / installed` 四个字段，
`SKILL.md` 正文是空的；`agent.skillIds` 除了序列化没有被任何逻辑读过。

工具落地后，技能才能填上内容。分两类：

| 类型 | 内容 | 例 |
| --- | --- | --- |
| **方法型** | 纯提示词 | `digest` 信息汇总、`translate` 翻译 |
| **能力型** | 需要工具 | `web` 网页检索、`remind` 提醒 |

**这类设计要在工具跑通之后单独做**，因为要定：技能的提示词放哪儿、
技能怎么声明它需要哪些工具、装了技能后工具是"多出来"还是"解锁"。

### 11.3 产物（后续）

`emit_artifact` 工具 + 导出/分享实装，是独立的一块。

### 11.4 其他

- 并行工具调用
- 工具调用的流式进度（"正在调用 X"）
- 上下文压缩（对话变长后的历史裁剪）
- 延迟加载工具（`ToolExposure` 那套，工具超过十几个再上）

## 12. 待确认

1. **`HttpClientFactory` 提到 public 的长期影响**——它是 `core:llm` 的内部设施，
   被 `core:data` 用之后就成事实上的公共 API。将来协议层要独立搬走时，
   是否拆出 `core:net`。
2. **`web_search` 的搜索后端**——需要一个搜索 API，等于又一把 Key。
   选项：(a) 只做 `web_fetch`，让用户直接给 URL；(b) 内置一个搜索服务商；
   (c) 复用对话的服务商（如果它有搜索能力）。**本期按 (a) 做，`web_search` 待定。**
3. **降级路径（文本协议）什么时候补**——本期只做原生工具调用。
   在只支持文本的服务商上，工具会用不了；现有的 ` ```task ` 机制能兜住一部分。
4. **`recall_memory` 的检索方式**——一期用关键词匹配，什么时候换向量检索。
5. **记忆的分层**——白皮书 4.2 提到会话/长期/任务三层记忆，现在只有一层。
   上工具之后，记忆的写入量会明显上升，分层可能要提前。
