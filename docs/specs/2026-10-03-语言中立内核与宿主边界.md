# 语言中立内核与宿主边界：第一批实现

日期：2026-10-03。对应白皮书 v2.1 Phase 2 的运行时边界、扩展装配及无头验证。

## 实际模块与职责

| 位置 | 职责与依赖 |
| --- | --- |
| `core:llm-contracts` | 模型请求、对话和响应事件，只依赖现有领域模型；保留 `core.llm` 包名，现有模型连接器继续使用同一类型 |
| `AgentLoopMachine` | 无 I/O 的状态推进、模型轮数预算和工具结果匹配，不调用协程、时钟或 JSON 解析器 |
| `AgentLoop` | Kotlin 协程宿主，收集模型流、驱动状态机、执行工具并调用释放回调 |
| `ToolCallExecutor` | 可替换的工具执行边界；默认 Kotlin 实现承担参数解析、确认、超时与工具异常处理 |
| `ToolConfirmationPort` | 返回明确的 `Approved` / `Denied`，确认计时由执行宿主承担 |
| `AgentExtensions` | 每个宿主自己的扩展集合，按装配顺序贡献工具和 Prompt，拒绝重复扩展 ID 与工具名 |
| `core:data` | 组装移动产品的扩展、平台端口、操作展示文案与设备会话收尾 |
| `samples:headless` | 同步和协程两种宿主驱动同一核心，验证结果、历史、工具事件和释放行为 |

运行时依赖现在是 `agent-runtime → llm-contracts / tools → model`，不再经过
`core:llm → core:platform`。网络和语音实现仍由具体连接器与产品使用。

## 核心推进协议

一个执行轮拥有一个 `AgentLoopMachine`，由宿主串行推进：

| 当前状态 | 输入 | 下一步 |
| --- | --- | --- |
| `Ready` | `start()` | 预算允许时返回 `CallModel`；零预算直接返回轮数上限 |
| `AwaitingModel` | 成功模型结果，无工具调用 | `Done`，最终回复文本单独返回 |
| `AwaitingModel` | 成功模型结果，包含工具调用 | 将 assistant 调用轮加入历史，返回 `CallTools` |
| `AwaitingModel` | 模型失败 | `Failed`，不执行该响应携带的工具调用 |
| `AwaitingTools` | 完整工具结果 | 按原始调用顺序回喂，预算允许时返回下一个 `CallModel` |
| 未完成状态 | `cancel()` | `Cancelled`，禁止继续递交模型或工具结果 |

核心规则：

- 轮数预算计算模型请求数量，包括第一次请求；工具完成后的结果即使遇到预算上限也保留在历史中。
- 同一模型轮的工具调用 ID 必须非空且唯一；每个结果必须匹配本轮调用，完整且恰好一次。
- 工具可以按任意顺序返回结果，回喂顺序按原始调用顺序确定；工具错误也是可回喂的结果。
- 缺失、重复或外来的结果，以及不符合当前状态的推进，会明确报错，不推进内部状态。
- `history()` 返回输入和已形成的工具调用/结果轮次；最终纯文本回复由宿主按产品需求组织和持久化。
- 状态机不持有模型凭据、网络客户端、平台端口或线程；列表结构与宿主提供的数据分离。

本阶段没有实现状态机的持久化恢复、总时长或总工具数预算，这些需求应先定义语义再演进。

## 宿主执行、确认与生命周期

默认宿主保留 30 次模型请求、30 秒工具超时和 5 分钟确认超时，允许按需要配置。
`Tool.confirmationRequired(args)` 由工具声明本次操作是否需要按策略确认，运行时
依据 `ExecutionPolicy` 和 `alwaysConfirm` 判断，不根据工具名特判。

移动端通过 `UserInputToolConfirmation` 将已有提问卡片接入结构化确认：只有精确的
“允许”选项（允许首尾空白）代表批准，否定或含糊文本均拒绝。其他宿主可以替换
`ToolConfirmationPort`，直接返回结构化结果。

`ToolHost.onTurnFinished` 由宿主显式提供，在成功、失败、超时结束或外部取消后
调用一次。Kotlin 宿主在 `NonCancellable` 上下文完成释放；移动产品把设备会话
收尾绑定到此回调。直接构造 `ToolHost` 的其他调用方也须提供其需要的释放逻辑。

操作确认和执行步骤的移动展示文案已移入 `core:data/ToolPresentation.kt`；
通用运行时默认使用工具名，产品可注入自身描述函数。

## 扩展装配

移动产品默认保持现有九个扩展，可在构造时追加、筛选或替换：

```kotlin
AppState(extensionFactory = { state ->
    builtinExtensions(state) + MyExtension()
})
```

工厂在应用数据恢复前运行；依赖记忆、技能等数据的扩展通过闭包延迟读取。
`AgentExtensions` 复制装配列表，保持宿主间的集合隔离，并按当前 Agent 动态生成
工具与 Prompt。扩展对象内部的可变状态及资源由扩展作者和装配宿主管理。
动态 MCP 工具同样由 `McpExtension` 贡献，产品没有装配该扩展时不会因全局已连接
Server 而自动获得 MCP 工具。

## 无头运行与共同用例

在 `StarAgentApp/StarAgent` 目录运行：

```powershell
.\gradlew.bat :samples:headless:run
.\gradlew.bat :core:agent-runtime:jvmTest :core:data:jvmTest
```

示例使用固定模型响应和真实加法工具，在同步宿主与协程宿主上验证相同行为。
运行前的依赖检查禁止携带 App 数据层、平台实现、Compose、Ktor 和本地语音模型。

共同用例位于 [agent-loop-cases.v1.json](../../StarAgentApp/StarAgent/core/agent-runtime/src/commonTest/resources/agent-loop-cases.v1.json)。
格式 1 描述初始用户文本、模型请求预算、模型/工具/取消事件，以及预期动作序列、
轮数和历史角色。它不依赖 Kotlin 测试代码，可供后续语言实现读取；当前 JVM 测试
执行这些用例，额外单测覆盖非法推进、工具结果匹配、取消和授权行为。

## 当前边界与后续工作

本批验证了同一核心的两种执行机制和移动产品实际扩展接入。iOS 目标只做 klib
编译检查，真机及模拟器运行仍需 macOS 环境；Linux 硬件、真实模型/音频和其他语言
实现均需另行验证。

后续继续处理：

- `core:data` 通用会话及持久化与 Compose 展示状态的分离；
- `ToolHost` 固定端口的按需能力访问、缺失能力及资源作用域；
- `core:llm` 中语音/平台实现的进一步拆分；
- 在目标设备上验证全双工音频及具体产品形态。

现有模型仍共享序列化、日期等领域类型，Kotlin 宿主使用协程和 JSON 解析。
这些依赖保留在明确边界内，后续按真实替换或移植需求继续评估。
