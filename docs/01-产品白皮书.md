## 摘要与战略升级说明

**星环智能 Agent（StarAgent）**最初诞生于移动端手机助手应用。v2.0 确立了向**跨形态、跨平台的通用智能体底座（Agent Substrate & SDK）**演进的战略方向；v2.1 进一步明确这条路线的设计原则与工程取舍。

**StarAgent 以语言中立的核心语义为设计方向，采用清晰的契约和可替换的执行机制，尽量降低对平台、框架及外部库的耦合。优先保持职责边界和行为一致性，在必要处接受明确、可控的工程依赖。**

当前采用 **Kotlin Multiplatform（KMP）** 开发参考实现，复用现有代码与生态能力。长期希望 TS、Rust、C/C++ 等语言能够以较低成本实现相同的核心语义；跨语言迁移用于检验解耦质量，具体语言版本按真实需求推进。纯逻辑、极少依赖是持续靠近的理想状态，当前优先兑现清晰的职责边界与可替换性。

遵循**“微内核 + 插件积木（Microkernel Architecture）”**的思路，核心保持克制，产品通过宿主、扩展与平台适配器组装能力。规划覆盖以下形态，各形态的支持状态与能力边界须分别验证：

- **桌宠机器人（Desktop Pet Robot）**：物理具身动作、表情屏幕、传感器事件、主动好奇心与自发心跳；
- **智能家居中控（Smart Home Gateway）**：无头后台守护、Matter/IoT 原语控制、全双工远场交互；
- **情感陪伴数字人（Emotional Companion）**：拟人心理状态机、长程情景记忆、情绪共鸣与深度关怀；
- **移动随身助理（Mobile Assistant）**：跨应用屏幕自动化操作、离线语音、IM 渠道触达。

一句话概括产品主张：**以统一的核心语义和可组装的执行能力，支撑多种软硬件形态中的感知、交互与行动。**

## 1. 产品定位与战略目标

### 1.1 一句话定义

StarAgent 是一个以**语言中立的核心语义、清晰的契约和可替换执行机制**为设计方向的跨端通用智能体底座与 SDK，当前以 Kotlin Multiplatform（KMP）作为参考实现，支撑桌宠机器人、智能家居、情感陪伴软件与移动助理等产品形态。

### 1.2 战略愿景

打破传统 AI Agent 局限于“屏幕文字输入框”的狭隘现状，让智能体具备全双工语音、物理环境感知、拟人心理状态机与现实工具操作能力，成为开发者构建下一代具身实体与数字伴侣的通用大脑。

### 1.3 核心目标

1. **核心语义统一（Portable Core Semantics）**：以明确的数据模型、状态变化和执行规则表达 Agent 行为，尽量减少 UI、平台 API、特定异步运行时及外部库对核心契约的影响，为低成本跨语言实现创造条件。
2. **执行机制可替换（Replaceable Execution）**：由宿主承担模型与工具调用、计时、调度和资源管理；当前可以继续使用 Kotlin 协程及成熟库，通过明确边界控制依赖，逐步支持无头运行与第二种产品形态。
3. **能力按需组装（Capability Decoupling）**：通过能力契约、扩展与适配器接入舵机、屏幕、传感器、语音、设备控制等能力，显式表达可用性、限制及生命周期。
4. **自然交互与持续记忆（Interaction & Memory）**：将可打断语音、情景记忆、情绪表达与自主感知作为可选择的能力扩展，兼容 `agentskills.io` 与 MCP，按具体产品场景验证效果。

体积、冷启动、内存与延迟通过目标设备基准测试衡量，并区分核心代码、运行时依赖和模型资源。具体指标与 JVM / Android / iOS / Linux 的支持等级均为 **【待确认】**，随实现与实测更新。

### 1.4 四大典型产品形态规划

| 落地形态 | 典型载体 | 核心特征与交互方式 | 关键技术扩展 |
|---|---|---|---|
| **桌宠机器人** | 桌面实体、树莓派/Linux 主机，ESP32 可作为外设节点 | 物理舵机/肢体摆动、小液晶屏表情、触摸/碰撞传感器响应、空闲时自主好奇心心跳 | 舵机控制、表情渲染、传感器事件流、自主心跳循环 |
| **智能家居中控** | 无头网关（Headless Linux/车机/微型主机） | 纯远场语音控制、全屋 IoT 设备原语操作、家庭多环境传感器事件联动决策 | Matter/MQTT 驱动、全双工回声消除、无头会话路由 |
| **情感陪伴软件** | 手机/桌面 3D 虚拟人、跨平台独立 App | 拟人情绪状态、长程情景自传记忆、主动关怀与情绪共鸣、语气词与伴随动作 | 可替换的情绪状态机、用户画像、动作代码映射 |
| **星环移动随身助手** | Android / iOS 原生应用，能力按平台分别提供 | 随身携带、语音、手机文件与多模态识别、IM 渠道联动，按平台支持设备操作 | Android 无障碍控制器与悬浮球、语音及媒体适配器 |

### 1.5 核心设计原则

1. **语义统一（Unified Semantics）**：核心表达任务如何推进、状态如何变化、权限与执行限制如何判断。数据、事件、结果和错误含义应明确，避免让某个框架的默认行为成为隐含规范。
2. **微内核与无头化（Microkernel & Headless First）**：核心语义与产品 UI、聊天卡片、具体硬件和应用生命周期分离。核心状态能够脱离 UI 被读取、推进与测试；Kotlin 宿主可以通过 `Flow` / `StateFlow` 向外提供观察接口。
3. **机制可替换（Replaceable Mechanisms）**：模型请求、工具执行、网络、存储、语音、计时和并发调度具有明确边界。替换实现时尽量保持核心规则稳定。
4. **依赖有归属（Bounded Dependencies）**：优先使用语言基础能力与窄接口，允许成熟库承担合适的实现职责。外部库尽量封装在所属层；公共契约暴露库类型或语义时，须说明必要性、影响范围和替换方式。
5. **平台差异显式（Explicit Capabilities）**：能力可用性、执行限制、权限和资源生命周期通过声明与适配器表达，各平台按自身约束实现。
6. **行为可验证（Verifiable Behavior）**：以受控输入验证状态转移、事件顺序、错误、取消与执行护栏；高危及物理动作应可审计、可中断。模型与外部环境的非确定性通过执行边界隔离。
7. **模型自由（Model Agnostic）**：通过模型契约与协议适配器接入 OpenAI、Anthropic 兼容服务及其他后端，端侧模型按需求适配。

### 1.6 理想状态与工程取舍

| 维度 | 长期理想 | 当前遵循的工程原则 |
|---|---|---|
| 核心逻辑 | 接近纯逻辑，主要依赖语言标准库 | 优先分清职责；必要依赖具有明确归属和可说明的成本 |
| 跨语言实现 | Kotlin、TS、Rust、C/C++ 可按同一语义较低成本实现 | 按实际需求选择验证语言，记录移植困难；不要求同步维护所有语言版本 |
| 执行结构 | 状态推进与副作用执行充分分离 | 保留可用的协程编排，逐步提取耦合点；状态机与宿主执行分离可作为演进手段 |
| 扩展与平台 | 新形态主要通过装配和适配接入 | 用真实的第二种运行形态验证边界，再调整抽象 |

统一的是职责边界、契约语义、依赖方向和生命周期约定。Agent 编排可以采用状态机，实时音频可以采用流水线，持久化可以采用仓储接口；各子系统选择适合自身时序与性能要求的机制。

判断设计质量的主要依据是：**增加一种产品形态或替换一种执行机制时，改动是否主要集中在装配和适配层，既有核心行为是否仍可验证。** 避免为达到形式上的零依赖、统一写法或预设模块数量增加复杂度。

真实场景揭示共用语义不足时，可以调整核心契约，并明确兼容影响及验证方式。设计原则用于帮助识别改动归属，核心抽象也随实际需求演进。

## 2. 行业背景与前沿生态对标

### 2.1 范式演进：从聊天框到具身与环境智能
当前 AI 正在经历第二波浪潮：从云端单一的“大模型问答”，走向与物理世界交互的“具身实体（Embodied AI）”与“环境智能（Ambient Intelligence）”。用户对机器人的诉求不再是冷冰冰的问答，而是像活物一样有小脾气、能感知触摸、能打断对话并真正控制实体设备。

### 2.2 前沿标杆生态拆解与启示

| 标杆项目 | 技术特色 | 优势与局限 | StarAgent 的汲取与定位 |
|---|---|---|---|
| **[JetBrains Koog](https://docs.koog.ai/why-koog/)** | Kotlin Agent 框架，支持 Android、iOS 等目标及持久执行、上下文压缩 | 提供丰富的编排与集成能力；端侧语音、硬件适配和资源成本需针对具体场景评估。 | 借鉴插件、持久执行与可观测设计，以实际接入成本和产品体验验证差异化。 |
| **[Rig AgentRun](https://docs.rs/rig/latest/rig/agent/run/index.html)** | 将 Agent 循环表达为 Sans-I/O 状态机，宿主执行模型与工具请求并交回结果 | 提供核心逻辑与执行机制分离的参考；这类分离本身不保证零依赖或多语言实现成本。 | 借鉴状态推进与宿主执行边界，按现有实现的迁移成本逐步采用。 |
| **[Oracle Open Agent Specification](https://github.com/oracle/agent-spec)** | 语言与框架无关的 Agent 定义及工作流规范 | 提供可移植的配置和组件语义；具体执行仍由各运行时实现。 | 借鉴语义规范与实现分离，明确 StarAgent 的数据、事件和执行规则。 |
| **LiveKit Agents / Pipecat** | 实时音视频与语音流水线 | 可参考其流式处理和打断设计；运行环境、音频后端及端侧适配成本需针对场景评估。 | 明确音频流水线与 Agent 核心的契约，允许宿主采用成熟音频库与执行机制。 |
| **[Honcho](https://github.com/plastic-labs/honcho)** | 面向有状态 Agent 的记忆基础设施与用户表征 | 源码公开并支持自托管；部署、推理与存储成本需按场景评估。 | 借鉴记忆构建与查询的职责分离，保持记忆契约可替换。 |
| **OpenClaw** | Gateway + Node 拓扑与设备能力节点 | 可参考其宿主与节点分工；第三方扩展的权限、来源和执行隔离需要独立评估。 | 借鉴能力节点解耦与扩展治理设计。 |
| **小智 AI (ESP32)** | 语音硬件与固件生态 | 设备固件、网关和模型服务的职责及资源限制需分别评估。 | 通过适配器接入硬件节点，按需求验证本地网关与 Agent 的分工。 |

### 2.3 差异化方向与验证依据

1. **统一语义与较低迁移成本**：通过明确的核心规则和契约降低不同宿主、平台及未来语言实现的接入成本，用第二种运行形态及按需跨语言试验验证。
2. **端侧交互与现实行动整合**：将本地语音、系统安全存储、云端或端侧模型及设备能力按需组装，验证实际交互质量、资源成本与控制可靠性。
3. **开放标准与轻量集成**：持续完善 `agentskills.io` 与 MCP 兼容性，明确支持范围、传输方式和执行环境要求。

KMP、Sans-I/O 和开放协议提供可借鉴的技术基础。上述方向能否形成持续优势属于 **【待确认】**，须以复用案例、接入成本、行为验证和用户体验数据支撑。

## 3. 范围边界与职责划分

为控制复杂度，StarAgent 区分产品、扩展与 SDK 的装配边界；SDK 内部进一步区分核心语义、宿主执行及可选适配。以下是目标职责划分，现有模块按需求逐步调整：

```
┌────────────────────────────────────────────────────────┐
│           Form Factors (产品形态层 - 各自独立发布)        │
│  StarAgent App │ Desktop Pet App │ SmartHome Daemon   │
└───────────────────────────┬────────────────────────────┘
                            │ 装配
┌───────────────────────────▼────────────────────────────┐
│         Capability Extensions (外围积木扩展库)          │
│  ext-motor │ ext-audio-duplex │ ext-emotion │ ext-device│
└───────────────────────────┬────────────────────────────┘
                            │ 依赖注入
┌───────────────────────────▼────────────────────────────┐
│       StarAgent Core SDK (内核与可选运行组件)           │
│  核心语义与契约 │ 宿主执行 │ 可选模型/平台连接器       │
└────────────────────────────────────────────────────────┘
```

### 3.1 内核 SDK 职责（Core In-Scope）

**核心语义与契约**负责：

- 表达多步推理与行动中的状态变化、待执行动作、执行限制及通用权限规则；
- 定义数据、事件、结果和错误模型，明确顺序、关联标识与取消含义；
- 定义模型、工具、上下文及能力访问契约；
- 定义扩展的贡献方式、能力要求与生命周期边界；
- 提供可在受控输入下验证的核心行为。

**宿主执行与可选连接器**负责：

- 驱动核心逻辑并分发事件；当前 Kotlin 实现复用 `TurnRunner`、`AgentLoop` 和协程；
- 执行模型与工具请求、计时、并发调度和取消，管理资源与会话生命周期；
- 提供 OpenAI / Anthropic 等协议适配、SSE 解析、HTTP 客户端与存储连接器；
- 根据语言和平台提供事件观察机制，Kotlin 可使用回调、`Flow` / `StateFlow`。

SDK 的发布包可以组合以上能力，但最小语义核心应尽量避免依赖完整网络、语音或平台实现。职责边界与实际构建依赖均需检查，当前模块的调整计划见第 7 节。

### 3.2 外围扩展职责（Extensions In-Scope）
- **具身硬件扩展**：舵机通信协议、屏幕表情渲染驱动、蓝牙/串口适配器；
- **语音管线扩展**：KWS 唤醒词、AEC 回声消除、VAD 断句、流式 TTS；
- **认知系统扩展**：`MemoryExtension`、`SkillExtension`、`EmotionStateMachine`；
- **设备控制扩展**：Android Accessibility 屏幕自动化、桌面命令行、系统通知；
- **智能家居扩展**：MQTT 客户端、Home Assistant 实体映射。

### 3.3 产品形态职责（Form Factors In-Scope）
- 负责具体的 UI/UE 展示（Compose Multiplatform 或无头守护进程）；
- 负责组装当前形态所需的具体扩展与硬件适配器；
- 负责最终产品的应用打包、分发与应用级生命周期管理。

### 3.4 严格排除项（Out of Scope）

- **核心语义与契约层不包含图形库**（包括 Compose、Java AWT/Swing 等），UI 依赖归属于产品展示与 UI 适配；
- **特定传感器协议、芯片驱动与操作系统 API 归属于能力扩展或平台适配器**；
- **单一形态的展示状态管理**（如手机聊天气泡维护）归属于产品侧；
- **外部库和执行运行时的具体机制须有明确归属**，公共契约暴露相关类型时说明其必要性及替换影响。

## 4. 总体架构设计（微内核 + 插件积木）

### 4.1 逻辑职责与依赖边界

以下展示目标职责与交互关系。数据和事件可以双向流动，代码依赖应通过契约收敛；这些职责可以先在现有模块内分离，按实际需求再决定是否拆分构建模块。

```
┌─────────────────────────────────────────────────────────────────────┐
│ 产品与装配：移动 App / 桌宠 / 家居守护进程                            │
│ 选择宿主、扩展和适配器，提供 UI、配置及应用生命周期                   │
└───────────────────────────────┬─────────────────────────────────────┘
                                │ 组装
┌───────────────────────────────▼─────────────────────────────────────┐
│ 能力扩展：记忆 / 技能 / 任务 / 语音 / 情绪 / 设备 / 硬件              │
│ 声明贡献、能力要求、执行限制与生命周期                               │
└───────────────────────────────┬─────────────────────────────────────┘
                                │ 通过契约接入
┌───────────────────────────────▼──────┐      ┌───────────────────────┐
│ 宿主执行                            │ 输入 │ 核心语义与契约        │
│ 请求执行、计时、调度、取消、资源管理 ├─────>│ 数据、状态、事件      │
│ Kotlin 协程 / 其他语言执行机制      │<─────┤ 推进规则、权限、限制  │
└──────────────────┬──────────────────┘ 动作 └───────────────────────┘
                   │ 调用适配器
┌──────────────────▼──────────────────────────────────────────────────┐
│ 模型与平台适配：HTTP / 存储 / 安全存储 / 音频 / 操作系统 / 硬件      │
│ 使用各平台的成熟库，实现契约并交回结果                               │
└─────────────────────────────────────────────────────────────────────┘
```

当前 `core:agent-runtime` 已包含无 I/O 的 `AgentLoopMachine` 与 Kotlin 协程宿主 `AgentLoop`。模型契约提取到 `core:llm-contracts`，运行时不再传递依赖网络、语音或平台实现；移动操作文案与设备收尾由产品宿主注入。`core:llm` 的语音实现仍依赖 `core:platform`，`core:data` 的会话与展示状态尚待分离。具体边界与验证方式见[第一批实现说明](specs/2026-10-03-语言中立内核与宿主边界.md)。

### 4.2 动态能力容器设计（IoC Capability Container）
计划将固定 12 个端口的 `ToolHost` 逐步调整为按需装配的能力访问机制。以下是 Kotlin 参考实现的简化示意：

```kotlin
// 纯解耦的能力容器
class CapabilityContainer {
    private val capabilities = mutableMapOf<KClass<*>, Any>()

    fun <T : Any> register(type: KClass<T>, instance: T) {
        capabilities[type] = instance
    }

    @Suppress("UNCHECKED_CAST")
    fun <T : Any> get(type: KClass<T>): T? = capabilities[type] as? T

    inline fun <reified T : Any> get(): T? = get(T::class)
    inline fun <reified T : Any> require(): T = get(T::class) ?: error("Capability ${T::class.simpleName} missing")
}
```
* **预期效果**：机器人扩展注册 `MotorPort`，移动端扩展注册设备控制端口，工具通过能力契约访问依赖。
* **语言边界**：`KClass` / `reified` 是 Kotlin 实现选择。跨语言共享的是能力标识、契约含义与可用性规则，各语言可使用适合自身的类型或显式标识机制。
* **工程要求**：在装配与运行阶段明确能力作用域、重复注册、缺失能力、并发访问和释放责任。容器、显式构造注入或其他机制按实际复杂度选择，避免将全局可变注册表作为默认设计。

### 4.3 自主感知循环架构（Sense-Plan-Act 循环）
桌宠与家居的感知、情绪与自主心跳通过可选扩展接入现有执行流程。传感器采集、计时与动作执行由宿主及适配器承担，核心按契约处理输入并推进任务：

                │        环境与传感器事件输入      │
                │ (人类语音/触摸感应/定时器/IoT)   │
                └───────────────┬───────────────┘
                                │
                                ▼
 ┌─────────────┐       ┌─────────────────┐       ┌─────────────────┐
 │             │       │                 │       │                 │

        │                                                 │

### 4.4 状态推进与宿主执行的演进方式

核心尽量表达数据和决策，由宿主执行副作用并交回结果。可在合适范围采用如下结构；它是设计示意，具体实现可保留必要的可变状态和现有编排机制：

```text
推进（当前状态，输入事件）→ 新状态、待执行动作
宿主执行动作 → 将结果或错误作为事件交回
```

输入可包括用户请求、模型分片、工具结果、确认结果、取消或计时到期；动作可包括请求模型、调用工具、申请确认、启动计时或保存状态。宿主处理网络、线程或协程、物理时钟和资源释放，核心规则尽量不依赖这些机制的具体类型。

演进时优先处理真实影响复用的耦合点，保留现有可工作的实现。必要的例外应说明原因、依赖范围、受影响契约和验证方式；出现实际替换需求时再评估进一步抽取的成本。

验证使用固定的输入、模型响应和工具结果，检查状态、动作及错误序列。第二个宿主或按需选择的第二种语言可以复用同一组用例；模型输出、外部设备与并发环境不同所造成的差异应单独记录。

## 5. 核心能力与扩展体系

### 5.1 认知与长程记忆系统
1. **语义事实记忆（Semantic）**：用户静态事实（偏好、关系、禁忌），采用结构化提取与受外部网页污染闸门保护。
2. **情景自传记忆（Episodic）**：按时间轴沉淀的事件轨迹（“某天与主人共同解决了什么难题”），支撑长周期羁绊建立。
3. **拟人心理状态机（Emotion State Machine）**：
   - 可采用 PAD 三维空间作为初始候选：`Valence`（正负情绪值）、`Arousal`（唤醒/精力程度）、`Dominance`（支配度），具体模型按产品效果选择并保持可替换；
   - 伴随系统提示注入实时心智状态：“你现在觉得很疲倦但很开心，说话语气带着轻微的撒娇”。

### 5.2 技能与开放扩展生态
- **标准对齐**：以 `agentskills.io` 规范为兼容目标，采用 SKILL.md 声明式元数据 + Markdown 指令，明确支持范围与技能的执行环境要求；
- **三层渐进披露**：
  - Level 1: 技能目录注入 System Prompt（名字 + 简述，每条 ≤200 字，总成本随目录规模增长，需控制目录预算）；
  - Level 2: 模型命中时通过 `use_skill` 按需加载完整正文；
  - Level 3: 附带参考资料通过 `read_skill_file` 按需延迟读取；
- **自主经验固化**：提供受限的 `create_skill` 工具，允许 Agent 识别到重复经验时向用户提出固化建议，用户同意后写入。

### 5.3 全双工拟人语音管线（Audio Pipeline）

- **流式分句与快速打断**：TTS 合成与 PCM 播放通过有界队列控制缓冲和背压；Kotlin 宿主可采用 Channel，实现队列清理、取消及静音切断，其他语言可选择对应机制；
- **回声消除（AEC）与唤醒词（KWS）解耦**：通过平台音频适配器持续采集，在设备自身发声时保持环境监听，能力与限制按设备显式提供；
- **验证边界**：语音流水线按实时要求独立设计，通过明确事件与 Agent 执行交互；打断延迟、误触发率和队列行为在目标设备上验证。

## 6. 安全、隐私与执行护栏

作为可能接触真实设备、电机舵机与私人生活的 Agent 底座，安全规则由统一契约表达，由宿主及适配器落实。以下是设计目标，现有实现须逐项验证：

1. **凭据存储契约（Credential Storage）**：
   模型 API Key、语音凭证通过统一契约访问，各端适配系统安全存储并明确实际保护等级；目标是敏感凭据落盘密文保护、备份范围可控，加密或读取失败须显式报告。硬件安全能力按平台与设备提供。
2. **三级权限控制与 AlwaysConfirm 机制**：
   - **只读操作**（查看日历、读屏检查、搜索）：直接放行；
   - **常规操作**（发消息、记便签）：跟随全局 `ExecutionPolicy`（Auto / OnDemand）；
   - **高危与不可逆操作**（安装技能、固化代码、转账、删除、大角度物理动作）：声明 `alwaysConfirm = true`，**无视全局自动模式，必须经由人类明确确认**。
3. **外部输入污染拦截（Prompt Injection Defense）**：
   同轮内一旦抓取过外部不受信内容（网页、第三方邮件），整轮触发“受污染”保护，禁止向持久记忆落库，禁止自动创建/更新技能。

确认结果应采用明确的结构化值，宿主负责取得用户输入，核心按授权语义判断。超时、拒绝和取消的处理含义须一致；当前轮次的污染标记是基础措施，跨轮来源追踪需进一步验证。迁移语言或执行机制时，上述规则应纳入共同用例。

## 10. 核心风险与应对策略

| 风险维度 | 具体风险表现 | 应对策略与设计保障 |
|---|---|---|
| **端侧算力与内存瓶颈** | 嵌入式硬件无法支撑大型模型或臃肿运行时 | 保持核心克制，分开测量核心、依赖与模型资源；重型语音/视觉能力按需装载和路由，预算经实测确定 |
| **跨语言语义偏差** | 错误、取消、顺序及运行时默认行为导致不同实现含义不一致 | 明确契约，使用相同受控输入检查状态和动作序列，记录语言与平台差异 |
| **抽象与依赖失控** | 为理想化零依赖或预设通用性增加层次，外部库类型又泄漏进核心 | 优先验证实际复用，说明必要依赖及例外，以替换成本决定后续抽取 |
| **物理动作安全风险** | 模型幻觉导致舵机过度转动或夹伤用户 | 动作指令通过硬件驱动层物理限位护栏（Physical Boundary Guardrails）硬性阻断 |
| **长程对话记忆膨胀** | 对话积累数月导致上下文爆炸与费用失控 | 引入滑动窗口 + 自动后台压缩（Compaction Pipeline）与情景摘要提取 |
| **全双工网络抖动** | 云端语音延迟导致人机对话“抢话”或“发呆” | 采用本地 VAD、有界缓冲与及时取消；打断反应时间 < 300ms 作为候选体验目标，测试口径与设备表现 **【待确认】** |

## 附录 A：核心术语表

- **Agent Substrate（智能体底座）**：负责认知编排、上下文调度、工具执行与状态流转的基础引擎，与具体硬件外设和图形界面无关。
- **Core Semantics（核心语义）**：数据、状态、事件、结果及执行规则的统一含义，尽量保持语言与框架中立。
- **Execution Host（执行宿主）**：驱动核心逻辑并负责副作用执行、计时、调度、取消及资源管理的运行环境。
- **Platform Adapter（平台适配器）**：使用具体平台 API 或外部库实现能力契约，并显式报告可用性与限制。
- **Sans-I/O（无 I/O 核心）**：将逻辑推进与实际输入输出分离的设计方式，核心交出待执行动作，宿主交回结果；可作为演进手段，本身不保证零依赖或跨语言实现成本。
- **Capability Container（能力容器）**：采用控制反转（IoC）机制按类型动态注册与索取硬件能力的通用环境契约。
- **TurnRunner（单轮编排器）**：统一封装单次人机交互或自发事件驱动中“思考-工具-行动”闭环的核心调度器。
- **Full-Duplex Barge-in（全双工打断）**：机器人在说话或发声时持续监听环境，人类开口即刻静音切断的技术机制。
- **Emotion State Machine（情绪状态机）**：驱动智能体产生拟人心理变化与自发行为的动态向量数学模型。
